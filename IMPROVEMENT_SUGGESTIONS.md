# Improvement Suggestions Log

A running log of non-urgent suggestions raised during chatbot testing — things
that work fine as-is (or were just patched) but are worth reconsidering later.
Not a task list: nothing here is required reading before shipping. Pull an
item out into a real task (or `KNOWN_ISSUES.md`) when it becomes worth acting on.

| Date | Area | Suggestion | Status |
|------|------|------------|--------|
| 2026-09-16 (Wed) | `mcp-server/src/server.py` (`get_products_by_category`) | Results still aren't sorted by price, so "cheapest"/"most expensive" questions rely on the model doing list-min/max comparison itself over near-identical product names — a known weak spot for small/quantized models (see `KNOWN_ISSUES.md` #3). Consider deterministic backend sorting (`sort=price_asc`/`price_desc`) or a dedicated cheapest-in-category tool so these questions are answered by sorting, not model reasoning, regardless of model size or context window. | Open |
| 2026-09-16 (Wed) | `mcp-server/src/backend_client.py` + `src/server.py` tool results generally | Only `get_category_tree()` has been trimmed to a minimal payload so far (`KNOWN_ISSUES.md` #3, fix 1). `get_products` and `get_products_by_category` still pass through full backend product objects into the LLM's context on every call. Worth auditing those for fields the model never needs (timestamps, image URLs, raw description HTML, etc.) and trimming them the same way — reduces token cost and the amount of raw data available for the model to accidentally echo back as JSON. | Open |
| 2026-09-16 (Wed) | `src/orchestrator.py` (`ask()` tool loop) — stock hallucination, see `KNOWN_ISSUES.md` #4 | Force a fresh `get_product`/`get_products` call instead of trusting model memory whenever: (a) a follow-up asks for an exact price/stock figure on a product already named earlier in the conversation, or (b) the user's message expresses doubt (e.g. "sure", "wrong", "search again") — reuse the existing `WRONG_TOOL_REMINDER`-style system-reminder injection, keyed on a doubt-keyword check instead of a wrong-tool check. | Open |
| 2026-09-16 (Wed) | `src/orchestrator.py` (`SYSTEM_PROMPT`) — stock hallucination, see `KNOWN_ISSUES.md` #4 | Add an explicit self-correction instruction: when a prior answer in the conversation turns out to be wrong, say so plainly ("I misspoke earlier — the correct figure is X") instead of inventing a reason the number changed (e.g. "it's been updated"). Prevents the model from fabricating a false change-of-state narrative to save face. | Open |
| 2026-09-16 (Wed) | `src/orchestrator.py` (`ask()`, final answer) — stock hallucination, see `KNOWN_ISSUES.md` #4 | Add a post-hoc check before returning the final answer: verify any $/unit figures it contains actually appear in the tool result(s) fetched *that turn*; if not, force one more tool round instead of returning unverified text. | Open |
| 2026-09-16 (Wed) | `src/orchestrator.py` (`_build_seed_messages`, `MAX_HISTORY_MESSAGES`) | `history` is trimmed by raw message count and only ever carries prior `user`/`assistant` *text* — never the tool-call/tool-result messages that grounded earlier answers. A long-enough conversation can lose the grounding for an earlier product entirely (not just have it overridden by a hallucination). Consider carrying forward a small structured "facts fetched this conversation" block alongside the trimmed text history. | Open |
| 2026-09-16 (Wed) | `src/llm_client.py` + `docker-compose.yml` (`OPENAI_MODEL`) | Evaluated `qwen3:8b` (thinking off) as a replacement for `qwen2.5:7b`. Hands-on CPU benchmark against the real docker-compose stack (`ollama` service, no GPU passthrough working on this machine): qwen2.5:7b — 5/5 correct tool calls, ~4.5s warm avg. qwen3:8b with thinking genuinely disabled — 4/4 correct tool calls, ~2.8s avg (~1.6x faster). **Blocker**: thinking can only be disabled via Ollama's native `/api/chat` endpoint with a top-level `think: false` param; `llm_client.py` currently calls Ollama's OpenAI-compatible `/v1/chat/completions` endpoint via the OpenAI SDK, and in this `ollama/ollama:latest` build that endpoint ignores both suppression mechanisms tried (`think: false` in the body, `/no_think` prompt suffix) — thinking stayed on, latency ~54s for a trivial prompt. Research corroborates qwen3:8b as the stronger model generally (36T vs 18T training tokens, reportedly better tool-call error rates), but switching model names alone in `docker-compose.yml`/`OPENAI_MODEL` today would make things *worse*, not better. Swapping models is only worth it alongside a `llm_client.py` change to call `/api/chat` (or another way to force `think:false` through the OpenAI-compat path). Sample size was small (4-5 trials, one prompt, no multi-tool/ambiguous-prompt cases) — re-verify before committing either way. | Open |
